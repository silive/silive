# 生产部署手册（2026-08）

正式发布状态：**BLOCKED**。本手册是受控执行顺序，不构成当前生产操作授权。

## 角色与前置材料

执行前必须有：固定发布候选 SHA、数据库负责人和业务负责人双人审批、完整备份及恢复演练记录、维护窗口、生产结构只读报告、外部测试订单白名单、脱敏验证清单、最小权限临时账号和回退负责人。

当前本地迁移与清理执行器硬性限制为隔离库。不得在生产现场临时删除门禁；生产可执行版本必须先经过独立安全评审和同版本彩排。

## 执行顺序与停止条件

1. **固定发布候选 SHA。** 记录源代码、迁移、脚本和配置文件哈希。工作区不干净、SHA 不一致或产物不可复现：停止。
2. **完整数据库备份。** 同时备份配置和必要上传文件，验证备份可读及恢复点。没有可验证备份：停止。
3. **测试订单清理 dry-run。** 使用外部绝对白名单路径；不得按时间、数量、`user_token`、金额或状态匹配。出现未知关联或 `MANUAL_REVIEW`：停止。
4. **人工核对白名单。** 业务负责人和数据库负责人逐笔确认脱敏清单、库存和财务汇总。数量不一致：停止。
5. **执行测试订单清理。** 必须同时提供 apply 和二次确认参数，保存退出码与汇总；任一订单失败：整体按脚本结果停止。
6. **清理后只读复核。** 检查白名单剩余、白名单外变化、主数据、库存、财务和孤立记录。任一异常非 0：停止，不迁移。
7. **执行迁移 preflight。** 使用只读事务检查缺失对象、重复唯一候选、历史异常、旧 `user_token` 和 AI 开关。任何重复或历史异常：`MANUAL_REVIEW`，停止。
8. **停止旧服务和 Worker。** `pm2 stop very-simple-cms` 后确认没有支付财务、支付超时、通知、履约或退款 Worker 继续认领任务。不能确认完全停止：停止。
9. **逐个执行迁移。** 严格执行 `001`→`007`；每步保存开始/结束时间、退出码和结构差异。任一步非 0：停止，不执行后续文件。
10. **每步结构验证。** 使用 `SHOW CREATE TABLE`、`DESCRIBE`、`SHOW INDEX` 和 `information_schema` 核对字段类型、默认值、唯一键、Worker 索引、InnoDB 与 `utf8mb4_unicode_ci`。不一致：停止。
11. **部署新后端。** 仅部署固定 SHA；`STARTUP_HISTORY_COMPENSATION_ENABLED=false`，不得在启动时补历史财务、成员、通知或业务键。
12. **保持 AI 关闭。** 明确设置 `AI_PREVIEW_ENABLED=false`，并确认没有 OpenAI 密钥被该服务加载。路由不是 404：停止。
13. **健康与 Worker 检查。** 验证健康接口、支付财务/超时 Worker ready、失败任务和重试速率；出现重试风暴、未知写入或外部通知异常：立即停 Worker 和新服务。
14. **创建虚构内部测试订单。** 验证 `user_id` 非空、`user_token` 为空；不要使用真实客户信息。失败：停止。
15. **双微信账号隔离。** 验证列表、详情、支付、退款、售后和旧会话边界。任何越权：停止。
16. **小额支付与部分退款。** 仅在财务批准后进行，验证交易唯一、Outbox、退款数量、库存释放事件和三类财务冲正。任何不平：停止。
17. **确认库存和财务。** 执行最终只读一致性 SQL；异常必须全部为 0。之后才可进入小程序上传审批。
18. **最后上传小程序。** 上传、提审和发布是独立审批步骤；后端验证未全部签字不得上传。

## Worker 停止与恢复

- 迁移前停止承载 Worker 的全部后端实例，确认无旧进程、定时器或其他主机仍连接数据库。
- 迁移期间不得单独启动 Worker。
- 新服务先以单实例启动并观察；确认表结构、队列量和错误率后，才逐步恢复其他实例。
- 恢复前记录 `payment_finance_outbox`、`order_payment_timeout_jobs`、`order_notification_records` 和履约/退款任务各状态数量。
- 出现失败积压或重试风暴：先停止 Worker/新服务，保留任务行和日志，不删除失败记录，不通过改状态掩盖问题。

## 失败与回滚原则

### 代码回滚条件

健康接口失败、启动缺表/缺字段、Worker 重试风暴、新订单身份字段错误、越权、支付/退款/库存/财务不一致、未知外部调用或一致性异常非 0，均触发停止与代码回退评估。

### 数据库迁移后的限制

- 数据库迁移完成后不能盲目切回旧代码；先确认旧代码是否能容忍新字段、新表和新任务状态。
- 不得把 `DROP` 新表、删除新列或清空队列作为默认回滚。
- 不得删除失败任务、财务 Outbox、库存事件或历史订单来“恢复正常”。
- 如果新旧代码不兼容，保持服务停止，由数据库负责人选择：向前修复，或在完整停机下从已验证备份恢复整个数据库和配套文件。
- 数据库恢复必须回到同一一致性时间点；不能只恢复个别业务表。

### 迁移中途失败

DDL 可能隐式提交。失败后立即停止后续迁移和所有 Worker，记录已成功对象；不要假设事务可回滚全部 DDL。修正方案必须在该“部分迁移结构”的克隆库重新彩排后才能继续。

## 必留证据

发布候选 SHA、备份校验、清理 dry-run/apply 汇总、preflight、每个迁移文件的时间和退出码、结构检查、启动前后行数、Worker 状态、新订单身份字段、双账号结果、支付/退款流水脱敏汇总、库存/财务终检和最终审批签字。
