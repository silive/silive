## 3. 架构与信任边界

### 3.1 组件

* 小程序：19 个注册页面；入口为 `app.js` / `app.json`，覆盖商品、购物车、订单、支付、推广、门店、自提、图片、协议和个人中心。
* 后端：Node HTTP 服务，主路由与数据协调位于 `cms/server.js`（约 1.2 万行）。
* 数据：MySQL 生产模式；存在 JSON 开发兼容，但生产启动校验要求 MySQL、`mysql2`、`sharp`、`qrcode` 等依赖。
* 订单域：`cms/order-domain.js`、`cms/inventory-ledger.js`、`cms/order-lifecycle.js`。
* 推广/门店：`cms/store-attribution.js`、推广奖励/门店结算记录。
* 异步任务：企业微信订单 Outbox、微信履约、退款同步 Worker。
* 静态文件：`/uploads/*` 由应用公开提供。

### 3.2 关键数据流及信任边界

1. 小程序传入商品 ID、数量、收货/自提信息、归因凭证；服务端必须重算价格、锁定库存、从 Session 取得用户身份。
2. 微信支付回调是高信任输入，但仍须验签、解密、主动查询并核验商户、AppID、订单、金额和交易号。
3. 门店归因令牌、邀请码、取货码均来自非可信客户端，服务端负责哈希保存、有效期、归属和一次性/幂等控制。
4. 管理员、业务员、门店、客户为不同权限域；浏览器 Cookie、用户 Session Header、资源所属门店/用户均为边界。
5. 企业微信和微信 API 是外部副作用；订单状态与财务账本应先事务提交，再由可恢复 Outbox 发送。
6. 上传内容及其元数据为不可信数据；公开 URL、图片解码和 EXIF 是隐私边界。

## 5. 独立发现问题

### BT-P1-01：支付事务与三类财务记录不具备原子一致性

* **影响**：支付订单可变为已支付且企业微信通知已入 Outbox，但个人推广奖励、门店推广佣金或业务员佣金中的一项/多项未创建。启动时补偿并非持续任务，可能导致财务统计和结算遗漏。
* **触发条件**：支付回调中订单支付事务成功提交后，进程崩溃、数据库短暂失败或任一财务记录创建失败。
* **代码位置**：`cms/server.js:6666-6750`。`markOrderPaidAndEnqueue()` 先完成订单和 WeCom 记录事务；随后 `markOrderPaid()` 在事务外顺序调用 `createRewardsForOrder()`、`createStoreSettlementRecordsForOrder()`、`createSalesAgentCommissionForOrder()`。
* **根因**：订单支付事实/企业微信 Outbox 与三类收益账本未纳入同一事务，也没有持续、可观测的缺失账本补偿 Worker。`ensureReferralRewardRecords()` 仅在启动调用（`cms/server.js:8878-8905,12145`）。
* **复现思路**：使第一个支付事务提交后第二个财务创建抛错；再次回调会得到已支付结果而提前返回，未自动重跑后续创建。
* **建议**：建立支付域 Outbox / 统一账本事件表；在同一 MySQL 事务内写入已支付事实和每个收益“待处理”事件，以唯一业务键幂等。事务提交后由 Worker 创建/补齐账本；增加周期性对账和告警，不依赖进程重启。

### BT-P1-02：有限库存的未支付订单没有发现超时关闭和库存释放机制

* **影响**：有限库存商品在创建订单时事务锁定并扣减库存。未付款、放弃付款或恶意批量创建订单不会自动释放库存，可能长期售罄、阻断正常销售。
* **触发条件**：任一有限库存商品存在；创建订单后不支付、不取消。
* **代码位置**：`cms/server.js:6340+` 的 `createOrder()` 与库存账本；扣减发生在订单创建事务内。现有 Worker 启动点为企业微信、履约、退款同步，没有找到未支付订单过期关闭/库存释放扫描任务。
* **当前证据**：静态搜索未发现“待支付超时关闭”定时任务；库存归还实现依赖取消、关闭或退款的状态入口。真实 MySQL 和生产商品库存模式未验证。
* **建议**：为待支付设置明确 TTL，创建独立且幂等的关闭任务，使用条件状态更新和库存归还账本；MySQL 并发测试覆盖支付与关闭竞争后再发布。

### BT-P1-03：匿名 AI 预览接口可被滥用消耗磁盘和外部模型额度

* **影响**：任何网络用户都可调用 `POST /api/ai/preview`。即使未启用外部 Provider，也会写入 SVG；启用 OpenAI Provider 时可触发外部 API 消耗。无用户绑定、限流、配额、任务上限或清理策略，可导致成本和磁盘可用性风险。
* **代码位置**：`cms/server.js:3315+`（预览生成及落盘）、`10825-10827`（公开路由）、`11221`（公开路由豁免）。
* **复现思路**：匿名重复 POST 大量不同参数，观察 `ai-preview-*` 文件持续增加；生产 Provider 配置为外部模型时还会产生请求量。
* **建议**：要求有效客户 Session/订单上下文或一次性上传凭证；按用户/IP 进行共享存储限流；限制并发、输入大小、每日配额和保留期；将文件写入纳入有上限的异步队列。

### BT-P1-04：小程序实际源码包已超过微信 2MB 限制，静态估算未能证明可上传

* **影响**：用户已收到微信开发者工具 `80051`：`source size 2227KB exceeded max limit 2MB`，当前版本不能上传。
* **当前证据**：`project.config.json` 使用仓库根目录作为 `miniprogramRoot`，并开启 `uploadWithSourceMap`。按当前 `packOptions` 的静态脚本计算约 840KiB，但与开发者工具实际统计矛盾，不能替代清理缓存后的真实上传统计。
* **建议**：在干净开发者工具中重新打开项目、清缓存并使用“上传前统计/依赖分析”；将 `miniprogramRoot` 精确限定为小程序运行根目录，稳定忽略后端、测试、文档、源映射和非运行资源。达到 `<=1.8MB` 并验证 19 页后才解除阻断。

### BT-P2-01：通用图片上传可保留原图及 EXIF/GPS，校验为“扩展名或 MIME”弱校验

* **影响**：上传原图可由 `/uploads/*` 公开访问。手机 JPEG 的 EXIF/GPS、设备型号和拍摄时间可能随原图暴露；仅以 `.jpg` 扩展名即可通过通用图片校验的逻辑也削弱了文件类型防护。
* **代码位置**：`cms/server.js:1981-2010` 的 `validateImageFile()` / `validateUploadFile()`，以及静态上传路径处理（`10355+`）。优化变体会生成 WebP，但通用上传返回仍包含原始 URL。
* **当前证据**：本地忽略的 `cms/uploads` 中发现多张 JPEG 保留 GPS/设备 EXIF。未查询生产引用，故不能断言这些具体文件在线上对外暴露。
* **建议**：通用入口也以 magic bytes/真实解码结果为准；对公开图片在保存前重编码并移除元数据，或将原图转为私有对象；对历史公开原图执行脱敏迁移并限制访问。

### BT-P2-02：管理员仍兼容明文 `ADMIN_PASSWORD` 环境变量

* **影响**：旧式明文管理员密码进入环境、进程查看或配置备份时暴露面较大。
* **代码位置**：`cms/server.js:2208-2217`。生产启动校验仍接受足够长度的 `ADMIN_PASSWORD`，而非仅接受密码哈希。
* **当前证据**：本地 `.env` 使用明文变量（值未读取/未输出）；生产配置未检查。
* **建议**：迁移为 bcrypt/argon2 哈希变量，生产启动拒绝明文管理员密码；轮换现有密码并限制环境文件权限。

### BT-P2-03：管理/业务员 Session 和限流均主要依赖进程内存

* **影响**：服务重启会丢失管理和业务员浏览器 Session；多 PM2 实例时限流按进程分裂，登录、上传、核销等保护可被横向放大。
* **代码位置**：`cms/server.js` 中 `sessions`、`salesSessions` 和多个 `Map` 限流器。
* **建议**：生产使用共享 Session/限流存储（如 Redis 或数据库受控表），明确 PM2 实例数；至少在单实例部署时记录并监控该前提。

### BT-P2-04：门店“货已到店/通知客户”并发下非原子，可能重复通知

* **影响**：两个并发单个/批量到店请求可同时读到旧状态、分别发起订阅消息；订单状态通常收敛，但客户可能收到重复提醒。
* **代码位置**：`cms/server.js:5878-5916`，`markPickupOrderArrivedForStore()` 先读后写且通知在条件更新之外。取货码核销路径已使用 MySQL 条件更新，是更好的参照。
* **建议**：使用 `SELECT ... FOR UPDATE` 或单条条件 `UPDATE` 原子认领到店动作，将通知纳入订单 Outbox 并以业务键去重。

### BT-P2-05：审核模式为硬编码且功能开关同时打开，发布治理不清晰

* **影响**：`utils/review.js` 将 `REVIEW_MODE=true` 固定在源码，支付、推广和门店开关也为 true；它仍会筛选首页入口。无法从环境明确区分审核/正式发布，容易产生错误功能面。
* **建议**：用经构建控制的发布配置替代硬编码；发布前以真机和首页配置确认实际入口，禁止仅凭常量名称判断。

### BT-P2-06：后台 CSRF 防护与 CORS 主要为同源假设，缺少统一令牌

* **影响**：后台/业务员 Cookie 会话依赖 Origin 检查和 `SameSite=Lax`，无显式 CSRF token；响应使用宽泛 CORS。没有发现直接可利用链，但防线不足以承受代理/浏览器边缘行为变化。
* **建议**：对所有 Cookie 驱动写接口强制可信 Origin/Referer 且引入 CSRF token；仅为需要的公开 API 设置 CORS，后台 API 不返回 `Access-Control-Allow-Origin: *`。

## 6. 已确认的积极控制（不等同于发布通过）

* 用户 Session 使用随机令牌，数据库保存 SHA-256 哈希；注销删除服务端 Session。订单创建会以服务端解析的身份覆盖客户端用户字段。
* 价格、订单商品快照、数量校验和有限库存扣减均由服务端整分/事务逻辑处理；库存扣减使用行锁与条件扣减。
* 微信支付回调含验签、解密、主动查询、商户/AppID/金额/订单校验；支付后订单与企业微信通知记录由 `markOrderPaidAndEnqueue()` 同一事务创建。
* 归因使用随机令牌哈希、有效期和门店校验；门店来源优先于个人推广；个人推广关系受唯一约束和循环/自荐检查。
* 取货码使用加密随机生成、唯一约束与门店权限校验；核销已有条件更新/一次性保护。
* 收益记录采用业务唯一键，退款/结算使用追加冲正和状态转换，未履约收益统计上归入预计收益。
* 企业微信订单 Outbox 有数据库唯一键、原子认领、超时恢复、有限重试和近期漏记录补偿。外部接口“发送成功但持久化 SENT 前进程崩溃”的窗口无法实现理论零重复，应保留告警和人工去重说明。
